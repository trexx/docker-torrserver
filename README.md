# docker-torrserver

A simple container image for TorrServer. It builds [TorrServer](https://github.com/YouROK/TorrServer), web UI included, into a single static binary in an otherwise empty image, published to `ghcr.io/trexx/docker-torrserver`.

## Overview

Torrserver custom image.

The [Dockerfile](Dockerfile) has four stages:

- `source` (`busybox:1-uclibc`) downloads the TorrServer release tarball from GitHub (currently `MatriX.148`) and unpacks it to `/tmp/src`.
- `front` (`node:16-alpine`) builds the web UI from `web/` with `yarn install` and `yarn run build`. Node 16 is what upstream's own Dockerfile uses: the web UI builds with react-scripts 4 (webpack 4), which needs it. This stage ships nothing at runtime.
- `server` (`golang:1.27-alpine`, pinned by digest) copies in the built web UI, runs `go run gen_web.go` to embed it, and builds the server with `CGO_ENABLED=0`, `-ldflags '-w -s'`, `-tags=nosqlite` and `-trimpath`.
- The final image is `FROM scratch` and contains only `/torrserver`, which is also the entrypoint.

The image contains no CA certificates and sets no `USER`.

## Usage

Images are published as `ghcr.io/trexx/docker-torrserver:<version>` and `ghcr.io/trexx/docker-torrserver:latest`. Release tags are TorrServer's release without the `MatriX.` prefix: `MatriX.148` is tagged `148.0`, `MatriX.146.1` is `146.1`.

The artifact generated by this repo can run standalone provided that CA certs are mounted somewhere or using distroless/static.
As an example,

```yaml
    spec:
      containers:
        - name: torrserver
          image: gcr.io/distroless/static@sha256:47b2d72ff90843eb8a768b5c2f89b40741843b639d065b9b937b07cd59b479c6
          command:
            - /app/torrserver
          volumeMounts:
            - mountPath: /app
              name: app
      volumes:
        - name: app
          image:
            reference: ghcr.io/trexx/docker-torrserver:148.0
```

Here the image is mounted as an image volume at `/app` in a `gcr.io/distroless/static` container, which provides the CA certificates, and `/app/torrserver` is run from it. In use, TorrServer's HTTP port (web UI and API) is 8090.

## Configuration

TorrServer is configured with its own command-line options, given as the container's arguments. Options in use with this image include `--path /data`, the directory TorrServer keeps its data in (mount a persistent volume there), and `--torrentaddr :8099`, the BitTorrent listen address.

## Development

Build the image locally with:

```sh
docker build .
```

The Dockerfile uses `RUN --mount=type=cache` for the yarn, Go module and Go build caches, which needs BuildKit (the default builder in current Docker).

Dependency updates:

- [`.github/workflows/upstream.yml`](.github/workflows/upstream.yml) runs daily (and can be run by hand). It compares the TorrServer tag in the Dockerfile with the latest `YouROK/TorrServer` release and, if they differ, opens an "Update TorrServer to <tag>" pull request on an `upstream/torrserver-<tag>` branch.
- [Renovate](.github/renovate.json) manages the Dockerfile. It keeps `node` below 17, because the web UI needs Node 16, and updates to build-stage images are disabled.

Workflows in `.github/workflows`:

- `container-check.yml` runs hadolint on the Dockerfile and builds the image without pushing it, on pull requests and pushes to `main`.
- `trivy.yml` scans `ghcr.io/trexx/docker-torrserver:latest` daily and uploads the results to the repository's Security tab.

## Releases

Releases are cut with the Release button: Actions → Release → Run workflow ([`.github/workflows/release.yml`](.github/workflows/release.yml), which calls `trexx/actions`' `release-image.yml`). Run it from the default branch.

1. It works out the tag from the TorrServer release in the Dockerfile's download URL, without the `MatriX.` prefix: `MatriX.148` becomes `148.0`, `MatriX.146.1` becomes `146.1`. If that version was released before, it uses `<version>-N` for the rebuild (for example after a base image update). A tag can also be given by hand in the `tag` input.
2. It builds the image and pushes it as that tag and `latest`.
3. It creates the git tag and the GitHub release.

Ticking "dry run" only works out the tag and builds the image; nothing is pushed and no release is created. Old images are pruned from the package after a push (`latest` and the newest tagged images are kept).

Pushing a tag by hand still works: [`.github/workflows/build.yml`](.github/workflows/build.yml) builds and pushes the image for any pushed tag.
